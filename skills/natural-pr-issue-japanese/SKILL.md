# PR・Issue の本文

## 目指すもの

読み手が**本文だけ**を読んで、次の 2 つが分かること。

1. 何が起きたか（何をしたか）、なぜか
2. 自分に何を求められているか

リンク先（PR・Issue・仕様・決定記録・コミット）は、確かめたいときに開くソースであって、理解の前提にしない。
「#41 との違いを先に見てください」と書くと、読み手は #41 を開き、長い本文のどこを見ればよいか分からず、何を知りたかったのかを見失う。

そのうえで、読む気になる量にする。長い本文は読まれない。目に入るのは要点だけにし、細目は開けば読めるように畳む（書き方 7・8）。

## 書き方

### 1. 概要で大枠を示す

概要は、詳細を読まなくても大枠が理解できるものにする。この PR（Issue）が何を、どういう方向で対応したのか（したいのか）が、概要だけでおおまかに分かるようにし、続く節はその詳細にする。

- 概要の各項目には、何を直したか（問題）と、どういう方向で直したか（対応）の両方を書く。問題の一覧だけで終わらせない
  - ✗ `次の 2 件を対応しました。` の後に「1. 試用環境でサンプルの案件が出ない」「2. 型エラーが 30 件残っている」と問題だけを並べる
  - ○ 問題の下に対応の方向を 1〜2 行添える

    ```markdown
    1. 試用環境でサンプルの案件が出ない
       - デプロイ時にサンプルデータを投入し、試用環境でもサンプルの案件が出るようにした
    ```

- 判断を仰ぐ論点があれば、概要でその中身を一言で示す（「develop の修正と逆方向のため、どちらを採るかご判断ください」だけでなく、それぞれがどういう方向なのか）
- Issue の概要は、何が起きているかと、どういう方向で解決したいか（提案）
- 書いたら、概要だけを読んで大枠が分かるかを確かめる

### 2. 参照先の中身を本文に書く

- ID や番号（要件・仕様・決定記録の ID、PR・Issue 番号、コミット、ファイル）を出すときは、**この文脈で読み手が必要とする中身**を抜粋か要約で添える
  - ✗ `REQ-012 を変える`
  - ○ `REQ-012（サンプルデータの投入は開発環境だけで行い、試用環境では行わない）を、試用環境でも行うように変える`
- 中身は元資料を開いて写す。記憶や推測で要約しない
- 読み手がすでに知っている中身まで要約しない（知っている読み手には冗長になり、かえって負荷になる）
- 「詳細は #N」「〜を見てください」で済ませない。見たら何が分かるのかを本文に書く。それでも原文を読んでほしいときは、どこ（ファイル・見出し・行）を何のために読むのかを書く
- コード上の名前（関数・ファイル・設定キー）は、何をするものかを先に書き、名前は括弧で添える
  - ○ `試用環境ではサンプルリセット（resetSampleData）を動かさない`

### 3. 番号の参照を箇条書きの途中に置かない

GitHub は、箇条書きの項目の中にある `#41` や PR・Issue の URL を、タイトル付きで展開する（地の文では `#41` のまま）。項目の途中にあると、主語と述語のあいだに長いタイトルが挟まる。

- 文中では内容で呼ぶ（「サンプルリセットを止める PR」）
- 番号は段落の終わりの `参照:` 行にまとめ、この文脈での役割を添える（`参照: #41（サンプルリセットを止める PR）`）。`参照:` 行は地の文なので展開されない
- 箇条書きの項目では、主語の位置や文の途中に `#N` を置かない

### 4. 同じものは同じ言葉で呼び、説明は初出に置く

読み手は上から読み、出てきた言葉を覚えながら進む。覚えた言葉と違う言い方や、まだ説明されていない言葉が出ると、前に読んだものと照合するために止まる。

- 予告（概要の箇条、「次の 2 件」など）と、その詳細の見出しは、文言と番号を揃える。予告を問題の形で書いたら、見出しも問題の形にする（対応の方向は、概要では問題の下に添え、詳細の節で展開する）
  - ✗ 概要「1. 試用環境にサンプルの案件が入らない」→ 見出し「1. 試用環境にもサンプルデータを投入する」
  - ○ 概要の項目も見出しも「1. 試用環境でサンプルの案件が出ない」
- 一度呼び名を決めたもの（「サンプルリセットを止める PR」）は、最後まで同じ呼び名を使う。文章に変化を付けるための言い換えはしない。呼び名を付けるときは「以下『…』」と明示する
- 避けるのは同義語への言い換え。代名詞や省略で済むところまで、名詞を繰り返す必要はない
- 同じものに呼び方が複数ある（試用環境、トライアル、trial）ときは一つに決める。使い分けるなら、初出で関係を書く（「試用環境（trial）」）
- 用語・略語・機能名（社内の略語、サンプルリセットなど）の説明は、最初に出てくる箇所に書く。後ろの節で説明していても、先に使うなら先で説明する
- 引用（仕様の文言など）は原文のまま。引用の中の呼び方は地の文に合わせなくてよい

### 5. 一つの段落・箇条に話題は一つ

- 箇条 1 つは 2 文までを目安にする。超えるなら小見出しと段落に分けるか、入れ子にする
- 比較や選択肢を「A は X、B は Y。どちらにするかは…で、…なら…」と一文に詰めない。選択肢ごとに箇条を分け、それぞれ「採ると何が変わるか」を書く
- 段落のあいだは空行で区切る
- 太字は段落の結論 1 か所だけ

### 6. 頼みごとを先に書く

- 判断・確認を頼むときは、何を決めてほしいかを見出しか冒頭の一文に書く。続けて背景、選択肢とその結果、推奨（あれば）の順
- 差し戻し・却下など、相手に不利な判断を伝えるときは例外。理由を先に書いてから判断を書く
- レビュワー向けの節では、頼みごと（判断・確認してほしいこと）を先に、共有だけのこと（知っておいてほしいこと）を後に置く。共有だけのことは畳む（書き方 8）

### 7. 敬体と常体を使い分け、敬体は短く

- 箇条書きは常に常体。内容（事実・変更・理由・確認結果）は常体で簡潔に書く（「〜を修正」「〜のため、〜とした」）
- 敬体は、レビュワーへの問いかけ・依頼と、箇条の前に置く導入の一文に限る（「下記を対応しました」「ご判断いただきたいことは以下の 3 点です」）。敬体で内容を書き連ねない

  ```markdown
  ## 概要

  前回のレビューで持ち越した 2 件を対応しました。

  - 試用環境にもサンプルデータを投入するようにした
  - REQ-012 が試用環境での投入を禁じていたため、試用環境でも投入するよう変えた
  ```

- コミットメッセージはこのスキルの対象外（リポジトリの規約に従う）

### 8. 重要でないことは書かない。書く必要があれば畳む

- 読み手が判断・確認に使わないことは書かない
- 残す必要はあるが判断には使わないこと（検証の細目、内訳、取り込んだ PR の一覧、CI やフックの回避の有無、別件のメモ、前回から変化のない事項）は `<details>` で畳む。`<summary>` の後と `</details>` の前に空行を入れる（無いと中の Markdown が描画されない）

  ```markdown
  <details><summary>その他（対応は不要です）</summary>

  - …

  </details>
  ```

- 畳まないもの: 判断・確認を頼むこと、変更の要点、書き方 2 で添えた中身の説明。判断に要るか迷ったら畳まない（畳んだ内容は見落とされる）
- CI が本文の書式を検査している章は、畳む前に検査の中身を読む。章内の全行を書式検査する CI では、`<details>` の行が書式違反になる

## 章立て

- PR: リポジトリのテンプレート（`.github/PULL_REQUEST_TEMPLATE.md` など）があれば従う
  - CI が書式を検査する章（チェックリストなど）は、書式を崩さない
  - 人が書くと決まっている章（判断の記録など）は、人の原文を貼るだけで書き換えない
  - 概要は大枠（書き方 1）。続く節で、変更点ごとに「何が困っていたか → どう直したか → どう確かめたか」を常体の箇条で
- Issue（テンプレートが無ければ）: 何が起きているか（現象、期待との違い、再現手順）→ なぜ問題か（影響）→ 求めること（決めてほしいこと、提案）→ 参照
- プロジェクト固有の約束（章の順、検査の制約、出典に書いてはいけない場所など）は、そのリポジトリの CLAUDE.md などに書いてあればそちらに従う

## 手順

1. 本文に出す ID・番号・ファイルを書き出し、それぞれの中身を元資料から 1〜2 文で抜き出す（仕様は該当行、PR・Issue は `gh pr view` / `gh issue view`）
2. 上の書き方で本文を書き、一時ファイルに保存する
3. 下の点検を通す。呼び名と初出は、見出しと各段落・箇条の先頭だけを上から読んで確かめる
4. [natural-japanese](https://github.com/coji/natural-japanese) が入っていれば、クイックモードで通す（`scripts/outline.py` で見出しと先頭文も抜き出せる）。CI が検査する章と、人が書いた章は直さない。敬体と常体の混在は、書き方 7 の使い分けなら直さない
5. `--body-file` で作成・更新する（`gh pr create` / `gh pr edit` / `gh issue create`）

## 点検

- [ ] 概要だけを読んで、何をどういう方向で対応したか（したいか）が分かるか
- [ ] リンクを全部消しても、読み手は何が起きたかと、自分に何を求められているかが分かるか
- [ ] ID・番号・コード名に、中身の説明が添えてあるか
- [ ] 箇条書きの項目の途中や主語の位置に、`#N` や URL がないか
- [ ] 予告した項目と、その詳細の見出しは、同じ文言・同じ番号か
- [ ] 同じものを別の言葉で呼んでいないか。用語・略語・機能名は、最初に出た箇所で説明しているか
- [ ] 2 文を超える箇条や、話題が 2 つ以上入った段落がないか
- [ ] 頼みごとが、共有だけのことより前にあるか
- [ ] 箇条書きはすべて常体か。敬体の文は、問いかけ・依頼と導入の一文だけか
- [ ] 判断に使わない内容が、畳まれずに出ていないか

## 例（PR の「レビュワーへ」）

✗ 書き直す前:

```markdown
- **PR #41 との方針の違いを先に見てください。** PR #41 は REQ-012「試用環境では行わない」を維持してサンプルリセットを止める方向、この PR は REQ-012 を変えて試用環境にもサンプルデータを入れる方向（DEC-07）。どちらにするかはレビュワーの判断で、PR #41 の方針を採るならこの PR から DEC-07 と `seed.ts` / `deploy.yml` の変更を落として型修正だけの PR にする
```

- 箇条書きの中の `#41` がタイトルに展開され、「PR fix: 試用環境の夜間リセットで…（…） #41 との方針の違いを先に見てください」と主語と述語が離れる
- REQ-012 の中身が「試用環境では行わない」だけで、何を行わないのか分からない
- 依頼、比較、代わりの案が一つの箇条に詰まっていて、決めてほしいことが最後まで出てこない

○ 書き直した後:

```markdown
### 1. 試用環境にサンプルデータを入れるか

試用環境でのサンプルデータの扱いが、この PR と develop に入っている修正で逆方向です。どちらを採るかご判断ください。

- 背景: REQ-012 は「サンプルデータの投入は開発環境だけで行い、試用環境では行わない」。一方、前回のレビューで「営業のデモは試用環境で行う」と決まり、試用環境にもサンプルの案件が要る
- **develop の修正の方向**: REQ-012 はそのまま。試用環境にはサンプルデータを入れず、サンプルリセット（夜間にデータを消し、サンプルから作り直す処理）も止めるため、試用環境ではサンプルの案件を見せられない
- **この PR の方向**: REQ-012 を「試用環境でもサンプルデータを投入する」に変え、デプロイ時に投入する（DEC-07）
- develop の修正の方向を採る場合: この PR からサンプル投入の変更（DEC-07、`seed.ts`、`deploy.yml`）を外し、型の修正だけ残す

参照: #41（develop の修正）、#35（「営業のデモは試用環境で行う」と決めたレビュー）
```
